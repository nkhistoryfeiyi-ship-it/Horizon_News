## [Spaghettifying DRAM](https://github.com/xoreaxeaxeax/skitter-creek-bath-salts) ⭐️ 7.0/10

Security researcher Christopher Domas released a tool called skitter-creek-bath-salts that manipulates the DRAM controller's address translation to scramble physical memory, bypassing higher-level protections. The tool is tied to his upcoming Black Hat 2026 talk and has been demonstrated on AMD Jaguar (2013) architecture, with notes about Zen 3 using different memory controller register base addresses. Modern DRAM controllers have grown enormously complex, requiring proprietary binary blobs just for basic access, which creates a massive attack surface. Once an attacker achieves ring-0 access on systems like Xbox or PlayStation, this technique could expose everything previously walled off, making console and embedded security groups particularly vulnerable. The tool scrambles the DRAM controller's address translation to bypass all higher-level protections. It currently works on AMD Jaguar (2013), with partial notes for Zen 3, but the full range of supported newer CPUs remains unclear. With ring-0 access, attackers gain access to memory regions hidden even from ring-0 itself.

hackernews · matt_d · Aug 13, 14:17 · [Discussion](https://news.ycombinator.com/item?id=49286341)

**Background**: DRAM (Dynamic Random Access Memory) is the primary working memory in computers, storing data that the CPU needs quick access to. Modern DRAM controllers handle complex address translation, refresh cycles, and power management, often relying on proprietary firmware blobs that are not publicly documented. Ring-0 is the highest privilege level in operating systems, granting unrestricted access to hardware. The increasing complexity of memory controllers has made them a growing target for hardware-level security research.

## [Single log line is 49KB+ (ext4) / 110KB+ (btrfs) of systemd-journald disk writes](https://github.com/systemd/systemd/issues/40262) ⭐️ 7.0/10

A systemd-journald bug reveals that a single log line can trigger disk writes of 49KB or more on ext4 and over 110KB on btrfs, demonstrating severe write amplification from journald's internal indexing and processing. This issue significantly impacts disk performance and longevity, especially on btrfs due to its copy-on-write nature, affecting Linux system administrators and engineers who rely on journald for logging. The amplification stems from journald's indexing and filtering mechanisms, with btrfs's copy-on-write exacerbating write overhead; users cannot easily filter or truncate logs for individual chatty identifiers.

hackernews · ValdikSS · Aug 13, 18:41 · [Discussion](https://news.ycombinator.com/item?id=49290215)

**Background**: systemd-journald is the logging component of systemd that collects structured log entries with metadata, stores them in binary journal files, and provides indexed querying. btrfs is a modern copy-on-write filesystem where each write can trigger additional data copies, leading to write amplification, especially for small, frequent writes.
